Core Features & Technical Functionality

A. Account Creation & Dual-Verification Authentication

Functionality: Users register using a phone number and an email address to ensure account security.

Mechanism: Phone number verification via Firebase Phone Authentication (SMS OTP). Email address verification via a 6-digit confirmation code.

Data Involved: Phone number, email address, unique user ID (UUID), and device installation identifier (device_id).

B. Local-First Financial Data Storage

Functionality: Users can manually log transactions, create categories, establish envelope budgets, and set savings goals.

Mechanism: All financial records are immediately saved to a local SQLite database (Drift) on the user's physical device.

Data Involved: Transaction titles, amounts, currencies, timestamps, payment methods, transaction types (income/expense), category names, envelope target amounts, and goal progress.

C. Automated Financial SMS Processing (Android only)

Functionality: Optional. Detects banking and digital wallet SMS messages from sender names you add yourself, and drafts transaction entries for you to confirm.

Mechanism: A background listener (RECEIVE_SMS / READ_SMS) checks each message on the device first. Messages that pass that check are sent as text to our transaction-extraction service, which returns a title, a category and a merchant name. The amount, currency and account details are read on the device.

Privacy Safeguard: Messages that do not pass the on-device check never leave the phone. One-time passcodes and verification messages are always rejected. No transaction is added to your records without your confirmation. See Android SMS Transaction Detection below for the full description of what is sent and what is not.

D. Cloud Synchronization Engine

Functionality: Keeps user data backed up and synchronized across multiple logged-in devices.

Mechanism: Uses an offline-first SyncOutbox queue pattern. Local mutations (create, update, delete) are logged locally and pushed to the cloud server via HTTPS when an internet connection is available. Implements Soft Delete (deleted_at tombstones) to synchronize deletions across devices before local database cleanup.

Data Involved: Encrypted financial records, operation timestamps, sequence IDs (sync_cursor), and operation status logs.

E. Analytics & Insights

Functionality: Generates visual reports (charts, monthly spending trends, category breakdowns).

Mechanism: Queries data directly from the local SQLite database. Optional AI models (e.g., Gemini API) may process anonymized transaction titles locally/cloud-side to suggest automatic categories.

Android SMS Transaction Detection

In Short: On Android only, and only if you switch it on, the app reads messages from bank senders you name yourself. Messages that look like transactions are sent to our servers as text so a draft transaction can be read out of them. Nothing is added to your records without your confirmation.

Where this applies

This is an Android feature. The app does not read SMS messages on iOS, and nothing in this section applies there.

The feature is entirely optional and is switched off until you switch it on. If you never switch it on, or you decline the SMS permission, the rest of the app works exactly the same and you add transactions by hand.

Permissions we ask for

Two Android permissions, and no others for this feature:

  • RECEIVE_SMS — to see messages as they arrive.
  • READ_SMS — to read messages already stored in your inbox.

The app cannot send SMS messages. It does not ask for permission to send them, and it never sends one.

Which messages we read

When you set the feature up, you type in the sender names your banks use — the short name that appears at the top of their messages. You also add the words that mark a message as a transaction. Both lists start empty. The feature cannot be switched on until you have added at least one sender and at least one word. We do not apply a built-in list of banks on your behalf.

The app looks at messages in two ways:

  • New messages, as they arrive on the phone.
  • Messages already on your phone. Once, when you switch the feature on, over a date range the app shows you before it begins. After that, only to catch up on messages that arrived while the app was not running.

Every incoming message passes through the app for a moment, because checking who sent it is the only way to know whether it is one of yours. A message from a sender that is not on your list is discarded on the phone straight away. It is not looked at any further, it is not saved, and it is not sent anywhere.

Checks that run on your phone

Before any message can leave your phone, it has to pass a series of checks that run entirely on the device:

  • One-time passcodes, verification codes and security messages are always rejected. This is the first check, before every other one. It cannot be switched off or overridden, including by words you add yourself.
  • Advertising and promotional messages are rejected.
  • Messages from senders that are not on your list are rejected.
  • A message must contain an amount, and either a currency or a word that describes a transaction.
  • Messages that only report a balance are rejected.

A rejected message goes no further. We record only a short code saying which check it failed — never the message, and never any part of it.

Many accepted messages never need to go any further either. When the app recognises a bank's message format on its own, it reads the transaction on the phone and sends nothing.

What we send to our servers

Please read this part. When a message passes the checks above and the app cannot read it on the phone, the full text of that message is sent to our servers so that a transaction can be read out of it. It is sent together with the names of the categories you use, so the transaction can be filed under the right one.

The text is sent as your bank wrote it. We do not remove or shorten anything in it beforehand. Anything your bank put in the message is sent along with the rest of it — the amount, any card or account digits the bank included, a reference number, the merchant's name, a balance.

The only changes we make are cosmetic ones that help the text be read: Arabic-Indic digits (٠١٢) are converted to Western digits (012), invisible formatting characters are removed, and repeated spaces are collapsed.

This travels over an encrypted (HTTPS) connection. No more than 120 messages per phone per day are sent this way.

Once a message reaches our servers it is used to produce the transaction and for nothing else. It is kept in line with "How long do we keep your information?" below.

What we do not send

  • Your bank list and your keyword list. Both are stored on your phone only. They are not part of your account, they are not backed up, they are not synchronised to your other devices, and they are never sent to us.
  • Messages that failed the checks. They never leave the phone, in any form.
  • Any record of who sends you messages. Where the app keeps a breakdown of senders to help us improve recognition, it stays on the phone.
  • Message text in usage statistics. When we record that the feature was used, we record counts, the currency, and a rounded amount range. No message text and no merchant name is ever included.

What is kept on your phone

The text of a message is stored in the app's own storage on your phone while the transaction it produced is waiting for you to review it. This is so you can check the draft against the message it came from.

When you confirm the transaction, or when you discard it, the message text is deleted. A small record stays behind without the text, so the same bank message cannot turn into a second transaction later.

A draft you never review stays in the review list, with its message text, until you review it or until the data is deleted as described below. It does not expire on its own.

Your controls

  • Switch it off at any time in Settings. It stops immediately, including for messages already waiting to be handled. Switching it off does not withdraw the Android permission itself — that stays yours to manage in your phone's system settings.
  • Edit your lists at any time. You can add or remove banks and keywords whenever you like.
  • Every transaction waits for you. Nothing detected in a message is added to your records automatically. You confirm each one, and you can change any detail before you do.

Deleting this data

When you log out, or when you delete your account, the app wipes its entire local database from the phone. The SMS review list, including any message text still sitting in it, is deleted first, before anything else. The app's stored settings are cleared at the same time, so your bank list, your keyword list and the on/off setting go with them.

Deleting your account also sends a deletion request to our servers, which removes the records held against your account. Logging out does not do this — it clears the phone only.

Sensitive System Permissions Required

To operate its core features, PayZabt requests the following system permissions:

  • RECEIVE_SMS / READ_SMS (Android): Optional, and switched off until you switch it on. Used to detect banking transaction alerts from sender names you add yourself. Messages from other senders, one-time passcodes, and messages that are not transactions are rejected on the device and are never saved or sent. Messages that pass that check are sent to our servers as text so the transaction can be read out of them — see Android SMS Transaction Detection. The app never sends SMS messages.
  • INTERNET & ACCESS_NETWORK_STATE: Required for Firebase authentication checks, background database sync, and connectivity status monitoring.
  • POST_NOTIFICATIONS: To send local budget alert reminders (e.g., overspending warnings) and goal achievement notifications.

Security & Data Retention Policies

  • Data Encryption: All network communication between the app and backend services uses TLS/HTTPS encryption. Local SQLite databases are stored in secure application-private sandboxes.
  • Data Retention: Personal and financial data is retained as long as the user maintains an active account.
  • Account & Data Deletion: Users can request full account and data deletion through the app settings or via a web contact form. Upon deletion, all cloud database records associated with the User ID are permanently purged, and local database files are wiped from the device upon logout.
